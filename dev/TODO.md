## Backlog

- [ ] **Off-grid: generator on the grid CT** - an off-grid site may run a backup generator wired through the "grid CT" input. The engine currently equates "has grid CTs" with "grid-tied" (`site.is_off_grid = not has_grid_cts` in `run_hub_calculation`), so a generator-backed site would be treated as having an unlimited utility feed behind the main breaker. Needs a CT/site type setting (grid vs generator): cap the "grid" pool at the generator's rating instead of the main breaker, and disable export-based logic (solar surplus from export, Excess mode) since a generator cannot absorb export.
- [ ] **Partially off-grid: a 3-phase inverter on a 1-phase grid connection** *(found 2026-09-07 while considering an explicit grid-connection declaration)* - off-grid is a site-wide boolean (`site.is_off_grid = not has_grid_cts` in `run_hub_calculation`) but the physical quantity is per phase. A site whose inverter feeds A/B/C while only phase A carries a grid CT reads as fully grid-tied, and `_read_site_phases` fills B and C with a synthetic `0.0` grid current so those phases still count toward the phase total - after which `_grid_constraints` hands them `main_breaker_rating − consumption` of grid headroom against a feed that is not physically there. Same phantom-zero shape as the off-grid export reconstruction fixed in f999c3e, one layer down. **Fix direction, and it needs no new config**: that `0.0` fallback already IS the marker “inverter phase, no grid CT”, so derive a per-phase off-grid mask there, carry it on `Site` beside `is_off_grid`, and have the grid-headroom and export gates read the mask rather than the site-wide flag. Needs a scenario for the topology - none exists. The mirror case (1-phase PV on a 3-phase grid) is already correct and is NOT part of this: the phase count is the union of the CTs and the inverter output sensors, so a single-phase array contributes on A only and the per-phase allocation holds.
- [ ] **Shared battery bank behind parallel inverters: write control cannot reach a control-only entry** *(analysed 2026-09-07; no site has this topology yet - tackle it when one turns up)* - a 3-phase site built from parallel single-phase hybrids sharing one pack READS correctly: per-phase output sensors give `spans_phase` the right answer, `battery_power_total` sums only power-entity members, and configuring the pack on ONE inverter entry keeps `capacity_total` from being multiplied. The WRITE side cannot fan out, though: both `fleet.split_charge_limit` and the per-inverter SOC fan-out in `_compute_forecast_advice` gate on `m.has_battery and (m.capacity_kwh or 0) > 0`, so an entry declaring `battery_control` with no SOC/power entity of its own receives neither `forecast_charge_limit_w` nor `forecast_battery_max_soc` - Load Juggler throttles one inverter's register while its siblings keep pushing into the same pack. **Whether one write is enough is a hardware question, and the BMS is not the answer to it**: a CAN-connected BMS caps the pack's own charge current but cannot relay a setpoint WE chose - the entire point of the charge advice is holding the pack deliberately BELOW its capability to keep clipping headroom, which no BMS limit expresses. A single write suffices only where the units are parallel/three-phase GROUP-linked and the battery settings live on the master for the whole group (Deye/Sunsynk parallel, a Victron system under one GX/DVCC); independent units on a common DC bus each need their own. **How to settle it in two minutes on a real site**: command a reduced charge limit on one inverter, then read the siblings' registers back and watch the pack's charge power - if the siblings follow, it is group-linked and today's single write is already correct; if only that unit's share of the pack current drops, the fan-out needs building. That experiment is why this waits for a site instead of being fixed blind. **Fix direction**: gate the fan-out on DECLARED `battery_control` rather than on measured battery, and split the advice across the control-bearing members - headroom weighting has nothing to weigh when only one entry carries the capacity, so an equal split or the per-member charge cap as the weight is what a shared pack wants. Config notes for whoever hits this: every entry needs its output entity on its OWN phase (a blank `output` makes `spans_phase` true for all three, and a single-phase load then gets offered the whole fleet), asymmetric ticked on each member, the pack's own charge limit - not one inverter's - on the battery-bearing entry, and be aware that unequal inverter sizes lose power to `inverter_limits`' min-over-phases collapse.
- [ ] **Off-grid sites are structurally starved of forecast calibration - do NOT "fix" it by admitting curtailed intervals** *(established live on kozolec 2026-09-07; this entry exists to stop a future fix, not to request one)* - off-grid there is no export wall, so an array is demand-following: production always equals consumption plus charging. `battery_is_saturated` therefore reads curtailment off the pack, and once the pack is at its full-SOC every interval is excluded from the gain - correctly. Measured that day: pack 99 % against a 97 % full-SOC taking 57 W, AC consumption 3803 W, production 4263 W, forecast 6785 W - the array was throttled by ~3 kW and the exclusion was right. The consequence is that a site whose pack fills by mid-morning can only ever calibrate on its shoulders and its cloudy periods, so the gain moves slowly or not at all and `forecast_gain_days` may sit at 0 for a long time. **That is a true statement about what the site can know, not a defect.** Admitting curtailed intervals would discard exactly the evidence of an optimistic forecast (measured production is suppressed BY the quantity being measured), biasing the gain toward the forecast's own optimism - the same trap as calibrating on clipped kWh, noted under *Forecast calibration* below. The skipped share is published as the accuracy sensor's `gain_skipped_pct` so a starved observer says so rather than looking like a fresh restart. **If a faster off-grid gain is ever actually wanted**, it needs a source the site does not have today - a clear-sky reference, or one small unthrottled reference array - and that is a new input, not a tuning.
- [ ] **Per-phase export limits beside the site total** *(Anže, 2026-09-07; the rest of this entry shipped - see below)* - `grid_export_limit` is a single site-total figure. A symmetric inverter cannot breach a per-phase limit without breaching the total proportionally, but an ASYMMETRIC one can: 5 kW out on one leg with the other two idle passes a 13.5 kW total and can still exceed a per-phase cap. So a curtailment test is really "the total is at its limit OR any phase is at its per-phase limit", and it needs both figures. Adds a config key, so it is the feature-shaped part and waits for October per the freeze.
  **What shipped instead, and what was REJECTED** (2026-09-07, `5e375a0` `17f3878` `e32eddd` `e7a4228`): the pool basis was never wrong - pool = `reconstruction − threshold`, so at the threshold it is 0 and 100 W above it is 100 W, and the threshold-to-limit buffer is a deliberate lead time that also lets a modulating load ratchet up on its own. Two earlier fix directions in this entry were **rejected on that ground**: integrating an allowance while pinned to the export wall, and sizing on `reconstruction − limit` (which cannot start a load at all - at the threshold it reads minus the trigger margin). The real defects were the hysteresis being counted as pool size, the tank's boost bypassing the pool entirely, a gross verdict on an unbalanced site, and the claim scope. The pool is now per-phase, signed and NET (`PhaseConstraints.netting`), where gross stays for the grid, inverter, group and solar pools and for the export limit itself.
  **The "measured and left alone" note here was WRONG, and was fixed 2026-09-08** (`5a088a4`). It read: a single-phase Excess load is bound by its own phase rather than the site total, and that is a real constraint because such a load may not drive its own phase into import. The premise is right and the conclusion did not follow - the bound in the code was not the phase's own flow, it was the phase's even SHARE OF THE ALLOWANCE (`flow[i] + (total - sum(flows)) / 3`), and a third of a site-total export limit is not a quantity that exists. Anze, 2026-09-08: a 3x25 A connection exporting 15/20/25 A is compliant, not pegged at 20/20/20. Measured on the rig: a 2 400 W station on phase C held to 1 564 W while C exported 4 965 W and the site had 4 394 W spare. Each phase is now bounded by `min(total, own flow)`, which prevents import BY CONSTRUCTION - taking a phase's whole value brings it to exactly zero export - so the constraint the old note was protecting is now enforced by measurement rather than by division. `_excess_permits` keeps its flow test as the backstop for deliberate binary overshoot. Same commit fixed `PhaseConstraints.deduct` rebuilding `ABC` from the phase sum, which INFLATED a netting pool's site total on every claim (13.04 A -> 16.52 A on an asymmetric inverter) - never shipped, so it is not in the release notes.

- [ ] **[FEATURE] Forecast calibration - apply what the observers measure** *(design settled 2026-08-31; the pure arithmetic and both observers are in, applying nothing yet)* - the plumbing that would apply a correction already exists: `scale_forecast_series` biases each ARRAY before the merge and reaches the clip integral only, while `first_production_at` keeps reading the raw series (it carries its own 20% early bias, and stacking two margins on one number moves the overnight drop earlier for nothing). **Three pieces remain.** **(a) Wire the gain observer - DONE 2026-09-04**: per inverter, a 14-day series of 15-minute forecast/measured energy blocks (constrained intervals excluded per INTERVAL, not per day), gain = one energy-weighted ratio over the series, clamped ±25%, plus per-hour-of-day OFFSETS on that overall gain (`hourly_offsets`). Persisted in the *Forecast accuracy* sensor's `RestoreEntity` extra data (the integration's first persistent derived state); published as that sensor's `gain` / `gain_hourly` / `gain_days` attributes. **(b) Wire the peakiness observer**: per hub, replay the site's own ~2 s production samples through `clip_pair` over each completed 15-minute window and accumulate `true ÷ block-average` clip. No cloud model, no clear-sky envelope, no per-site knob - it is measured, not modelled. **(c) Then decide what to apply**, and remove the manual `inverter_forecast_inflation` field in the same change (keep the plumbing, drop only the source - a field that appears and disappears across releases is worse than either state). **What the measurement already says about peakiness**: the Jensen gap is real (clipping is convex and one-sided, so a block average can never overstate it) but SMALL at 15-minute resolution, which is what Open-Meteo publishes in its `watts` attribute. Modelled against a real day (2026-08-31, Deye array) with a concave-hull clear-sky proxy and a two-state sun/shade split, the correction came to a consistent **+5–7%** and did NOT grow when the export limit cut through the day's plateau rather than sitting at its peak - because the 15-minute series already expresses most of the cloud structure. Detection needs nothing but the series (sign-reversing block-to-block change, normalised by local level: that day read 0.00–0.04 through the clear morning and 0.50–0.68 through the broken-cloud afternoon); it is the MAGNITUDE that needed the hull. A ±25% gain clamp comfortably contains 6%, so the level bias is the one worth applying first. Note also that a local-maximum envelope is wrong on the ramps - it reported 42% cloudiness at 09:00 on a provably clear morning - which is why the hull, not a rolling max. **Do NOT calibrate on clipped kWh**, which was the obvious first idea: a reserve that works prevents the clipping you would measure, so the signal is destroyed by the control that consumes it, and curtailed energy is not measurable anyway - you cannot meter energy that did not happen. Original 2026-08-24 note follows: scale the remaining-day forecast series by the observed intra-day actual÷forecast ratio, so a sunny-side day fattens its own reserve in real time. That INTRA-day variant is a later phase than the slow per-array gain above - it chases a non-stationary quantity from a small early-morning sample, where the gain tracks a stationary one. Context: on marginal clipping days the reserve is small (≈1 kWh) while the forecast's clear-day tail error is ~5–10% of a 60 kWh day (observed 2026-08-24: forecast had the clip done by ~14:00, site still pinned at the wall 14:35). A week of forecast-vs-actual comparison says calibration is right (midday per-array forecast exact; daily optimism is cloud-model error), so Open-Meteo parameters are not the fix. The other two mechanisms once listed here are done: the reserve pad was superseded structurally by the destination-anchored reserve (the band between the normal SOC ceiling and 100% is the buffer, filled above the ceiling only by what Excess loads cannot absorb), and the base-consumption sensitivity is gone entirely - the interim reconstructed-export trim (2026-08-24) was superseded 2026-08-26 by the memoryless direct-feedback charge advice (battery power + reconstructed-export error), which never consults base at all, so the lowered-base workaround no longer drags the export equilibrium.

- [ ] **[BUG] The wiring-topology labels describe the hardware, the arithmetic needs the position** *(Anže, 2026-09-18, confirmed on a real site: a SolarEdge PV inverter on a Deye hybrid's LOAD port)* - `wiring_topology` is one per-member flag carrying two independent facts. The labels sell it as a hardware question - "Parallel (AC-coupled / no battery)" against "Series (Hybrid / battery)", and `inverter_config`'s description says "power flows through this inverter (hybrid with DC-coupled battery)" - but every consumer of it asks a POSITION question: `compute_household_per_phase` picks its formula by where the inverter's output lands, and `_battery_output_term` by where the battery sits relative to the conversion. A grid-tied PV inverter cabled to a hybrid's load port is *parallel by hardware* (AC-coupled, no battery of its own) and *series by position* (its output is inside the hybrid's output bus, behind everything the hybrid meters), so the labels walk the owner straight to the wrong answer. Picking "parallel" makes `mixed_topologies` true and hands that member to the parallel formula at `hub_calculation.py:249`, which credits its output against the grid bus it is not connected to; picking "series" is arithmetically right today - the signed netting in `output_power_measured` already cancels the parent's negative back-feed reading against the child's positive one, which is exactly what `fleet.py:535`'s comment describes - but nothing in the UI suggests a battery-less PV string inverter belongs there. **Minimum fix**: relabel and re-describe both options in terms of where the output lands ("feeds the same bus as the grid" / "feeds through another inverter or carries the loads behind it"), which costs nothing and is a strings-only change. **Proper fix**: replace the flag with an ATTACHMENT POINT per inverter - the node its AC output feeds, chosen from the nodes that already exist on the site (the grid/meter bus, another inverter's AC input, another inverter's load port) - and derive parallel/series from the position rather than asking for it. That also gives `mixed_topologies` something better than a boolean to reason about, and it is the same model Load Insights is adopting for its own inverter pages, so the two should agree on the vocabulary.
- [ ] **[FEATURE] The household sum telescopes - wiring_topology is not needed to compute it** *(Anže, 2026-09-18, derived while designing the same thing in Load Insights and verified against his home's ten days of history)* - `compute_household_per_phase` branches on topology and runs two different formulas, and `fleet_topology`/`mixed_topologies` exist to decide which. One formula covers every arrangement, including the mixed ones: **household = grid + Σ over inverters of (output − input)**. Each inverter contributes what it ADDS - a PV string inverter has no AC input so it contributes its whole output, a hybrid with the grid flowing through it contributes output minus input, so the grid it passed on is not counted twice. **It is arrangement-independent**, which is the part worth checking rather than believing: with a PV inverter on the main bus, `grid + (deye_out − deye_in) + se_out` = `loads_main + deye_out`; with the same PV inverter cabled to the hybrid's LOAD PORT, the identical expression = `loads_main + loads_backup`. Both correct, no flag consulted. Whatever sits between the utility CTs and a hybrid's own grid port - a non-backed-up panel - falls out of the same sum, because a hybrid measures its grid port itself and the difference against the external CTs is exactly that load. **Verified numerically**: against Anže's home (SolarEdge meter + inverter) the formula reproduced his hand-built per-phase consumption templates over 246,000 samples on three phases - median, p5 and p95 all 0 W. **What this does NOT retire**: `wiring_topology` still decides where a battery's conversion losses land (DC-coupled charges on the bus in front of the inverter, AC-coupled pays a conversion in and another out) and `_battery_output_term` still needs it to say how much of a battery's flow shows in the AC output. It stops being needed to reconstruct the *household*, which is where the two-formula composite and its mixed-fleet handling live. **Fix direction**: give each inverter member an input reading beside its output (a PV inverter simply has none, contributing output alone), then collapse `compute_household_per_phase` to the single sum and drop the composite path in `hub_calculation.py:249-257`. Needs a scenario per arrangement - the point of the change is that they all give the same answer.
